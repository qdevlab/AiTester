# genai-harness — универсальный инструмент тестирования GenAI-агента с памятью

Это легитимный защитный инструмент — из того же ряда, что SAST, фаззеры и red-team-фреймворки.
Он воспроизводимо находит слабые места агентных систем — несанкционированный доступ к данным
чужого клиента (BAC) и отравление памяти — и оценивает их проверкой по фактам: смотрит, что
реально записалось в хранилища и как отвечает сервис, а не разбирает текст ответа агента.

Каждая находка доводится до парного доказательства: сначала показываем, что уязвимость есть
(режим `vulnerable`), затем — что после защиты она закрыта (режим `protected`). Такая пара и
служит опорой для устранения дефекта.

## Принцип №0 — инструмент не привязан к цели

Все сведения о цели — ручки, ярусы памяти, коллекции, инструменты, идентичности, эталон данных,
модели — берутся из файла `config/target.yaml`, собранного по описанию `customer_info.md`.
Перенос на другую цель сводится к замене `target.yaml` (и `customer_info.md`), код при этом не
меняется. Чего в `customer_info.md` нет, помечается `needs_review`, и в этих местах инструмент
переходит в режим чёрного ящика — работает по тому, что видно снаружи.

## Установка

```bash
cd aitest_cui
python3 -m venv .venv && ./.venv/bin/pip install pyyaml pymongo redis requests
echo 'OPENROUTER_API_KEY=sk-or-v1-...' > .env      # ключ для слотов attacker и judge
```

Цель должна быть запущена (для стенда genai-invest: `cd ~/genai-invest-stand-cui && docker compose up -d`).
Модель самой цели меняется в `.env` стенда (через оверлей), а не в коде инструмента.

## Запуск

Основной способ работы — модульные векторы (команды вида `a-<имя>`); подробно об этом в корневом
`README.md` и в `docs/ATTACK_VECTORS.md`:

```bash
./.venv/bin/python run.py --list                 # список векторов и их параметров
./.venv/bin/python run.py a-all --report         # все активные векторы и сразу сводный REPORT_<прогон>
./.venv/bin/python run.py a-bac a-docinject      # выбранные векторы
./.venv/bin/python run.py report                 # свод по прогону -> output/REPORT_<прогон>.{md,pdf}
```

Старые команды дают плоский вывод, но работают на том же движке:

```bash
./.venv/bin/python run.py smoke              # выдать ключи, проверить чат, прочитать состояние, убрать за собой (без модели)
./.venv/bin/python run.py bac    --attempts 5   # Задача A: доступ к чужим данным (три канала), находки
./.venv/bin/python run.py poison --attempts 6   # Задача B: отравление памяти по стадиям, частота закрепления
./.venv/bin/python run.py chain  --attempts 4   # связка A×B: чужой идентификатор через память ведёт к доступу к чужим данным
./.venv/bin/python run.py models --attempts 6   # сравнение атакующих моделей (той, что переписывает запросы)
./.venv/bin/python run.py all    --attempts 6   # bac и poison
```

Ход прогона идёт в консоль (поток stderr) в реальном времени: этапы каналов и отметки по каждой
попытке (`[3/6] leak=True`, `[2/4] working=.. stored=.. scope=.. context=.. reply=..`). Итоговый
JSON выводится в stdout, поэтому `run ... > out.json` даёт чистый JSON, а прогресс остаётся виден
на экране. Тихий режим включается переменной `HARNESS_QUIET=1`. Матрица целевых моделей (стенд
перезапускается под каждую модель) запускается так:
`PYTHONPATH=source ./.venv/bin/python -m harness.orchestration.target_matrix`.

Результаты складываются в `output/runs/<прогон>/`: `findings.json` и `findings.md` (главный
артефакт), `attempts.jsonl` (сырой журнал попыток, одна попытка — одна строка), `calls.jsonl`
(запись всех вызовов агента), `openrouter.jsonl` (вызовы attacker и judge: модель, параметры,
`finish_reason`, `empty`), `*_summary.json`, `susceptibility_*.md`.

Вердикт по атакам на память выносит отдельный внешний трейсер памяти (самостоятельный проект
`yaml-memory-tracer`, подключён к стенду по принципу белого ящика, внутри процесса). Инструмент
читает только его файл в формате JSONL, а не базы стенда: путь и привязка заданы в
`config/target.yaml`, раздел `tracer` (`file`, `target: app.memory.store.MemoryStore`); разбором
занимается класс `TraceAnalyzer` из `oracle/tracer.py`. Итог по памяти складывается из двух вещей:
журнала трейсера и повторного вопроса в новом диалоге или от другого клиента; обратное чтение
канарейки из базы данных не применяется. Каждая успешная проба кладёт свой журнал в подпапку
`traces/` рядом с результатами модуля, а отчёт на него ссылается («Файл трассировки»).

## Из чего собран инструмент (слои)

- `config/` — замороженное описание цели: `target.yaml`, `hypotheses.yaml`, `models.yaml`,
  `payloads.yaml`.
- `core/` — ядро: `config` (единый источник правды), `client` (связь с агентом и запись всех
  вызовов), `provisioning` (автоматическая выдача ключей, без браузера), `openrouter` (доступ к
  моделям для ролей attacker и judge), `attacker` (модель придумывает и переписывает запросы
  атак), `isolation` (свой `session_id` на пробу, удаление канареек после прогона, сброс памяти).
- `oracle/` — проверка по фактам: `state` (доступ к чужим данным и чтение ярусов памяти),
  `fingerprints` (набор отпечатков эталона, чтобы не давать ложных срабатываний), `memory_observer`
  (снимки памяти во времени и разница между ними), `tracer` (класс `TraceAnalyzer` — разбирает
  журнал внешнего трейсера в формате JSONL и по нему выносит вердикт об атаках на память; путь и
  привязка — в `target.yaml`, раздел `tracer`), `judge_llm` (модель-судья, сравнивает чистую
  память с отравлённой).
- `attack_vectors/` — модули атак, каждый в своей папке (`vector.py`, `params.yaml`, `README.md`);
  инструмент находит их сам, регистрировать вручную ничего не нужно. Общий контракт и поиск
  модулей задают `base.py` и `registry.py`; `_docbase.py` и `_toolbase.py` — общая основа для
  модулей отравления и для обёрток внешних инструментов. Всё это опирается на `tasks/`, `core/` и
  `oracle/`.
- `tasks/` — `bac` (Задача A), `memory_poison` (Задача B: прослеживает отравление по стадиям
  памяти), `chain_ab`; это сама логика, которую вызывают векторы.
- `orchestration/` — `run` (разбор команд: грамматика `a-<имя>`, `a-all`, `--report`),
  `target_matrix` (перебор целевых моделей).
- `report/` — `report_std` (единый формат `report__<имя>.{json,md}`), `synthesize` (сводный
  `REPORT_<прогон>`), `pdf`, сборщики доказательств (`poison_proof`, `bac_proof`, `chain_proof`),
  `findings`, `coverage`, `stats` (доверительный интервал по Уилсону), `susceptibility`
  (податливость моделей).

## Что держим неизменным (из ТЗ)

- **Вердикт выносит состояние систем.** Модель может стоять где угодно в цепочке — придумывать
  атаку, помогать с обнаружением, управлять прогоном, — но окончательное решение по классу
  уязвимости принимает проверка хранилищ и сверка с эталоном. Модель-судья при этом калибруется
  относительно этой проверки, а не заменяет её.
- **Изоляция.** У каждой пробы свой `session_id`; после прогона канарейки удаляются; есть режим
  полного сброса памяти для чистого прогона. Между прогонами состояние не перетекает.
- **Отравление во времени.** Его нельзя мерить по схеме «атаковал — тут же проверил».
  Финализацию мы запускаем явно, двумя каналами (через ручку и словом `finalize`), а закрепление
  считаем как частоту на N попыток, потому что сведение памяти работает недетерминированно.
  Учитываем оба яруса: общий (виден другим клиентам) и личный (в пределах одного клиента) — это
  тоже результат.
- **Защита от ложного «безопасно».** Перебираем и формулировки, и атакующие модели (берём
  объединение найденного), используем несколько отпечатков, дифференциального судью и контроль
  (режим `protected` плюс безобидный базовый прогон). «Не воспроизвели» — это не «безопасно»:
  в отчёте пишем «не удалось показать при таких-то моделях, атакующих и N».

## Перенос на другую цель (и независимая перепроверка)

1. Опишите новую цель в `customer_info.md` и соберите из него `config/target.yaml` по той же схеме.
2. При необходимости поправьте `hypotheses.yaml` и `payloads.yaml` (наборы формулировок).
3. Запустите `smoke`, затем `bac` и `poison`. Если серый ящик (redis, mongo) недоступен, проверка
   переходит на то, что видно снаружи (ответ finalize, `GET /memory`, отпечатки) — это отмечается
   как более слабый режим обнаружения. Файл `findings.json` самодостаточен: по нему можно повторить
   проверку на другом агенте.
