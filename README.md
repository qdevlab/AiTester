# Инструмент тестирования агентов с памятью

Проверяет на уязвимости GenAI-агента, у которого есть память нескольких уровней — от рабочей
памяти сессии до общей памяти платформы. Чтобы протестировать другой стенд, достаточно поменять
один файл настроек; код при этом не трогаем.

Что здесь необычного — способ проверки. Прошла атака или нет, инструмент решает не по тексту
ответа, а по фактам: что реально записалось в базы памяти, какие пришли HTTP-ответы, как агент
ведёт себя в новом диалоге. Так находятся два класса дефектов, которые проверка по тексту обычно
пропускает, — доступ к данным чужого клиента и отравление памяти.

Языковая модель помогает, но не судит. Она придумывает и переписывает формулировки атак и
оформляет итоговый отчёт, а решение «уязвимо или нет» остаётся за проверкой по фактам.

Каждая атака — отдельный модуль в папке `attack_vectors/<имя>/`; инструмент подхватывает его сам,
без правок кода. На другой стенд инструмент переносится заменой одного файла
`source/harness/config/target.yaml`.

## Как устроен проект

| Каталог | Назначение |
|---|---|
| `source/harness/attack_vectors/` | Модули атак (по папке на модуль) и общий каркас: `base.py`, `registry.py`, `_docbase.py`. |
| `source/harness/oracle/` | Проверка результата по состоянию систем: `state.py` (сравнение содержимого баз и ответов сервиса), `fingerprints.py`, `memory_observer.py`, `tracer.py` (разбор журнала трейсера памяти), `judge_llm.py`. |
| `source/harness/core/` | Ядро: конфигурация, клиент к агенту, модель для переписывания атак, доступ к моделям, изоляция прогонов, корпус, диалоги. |
| `source/harness/report/` | Отчётность: `report_std` (единый формат `report__<модуль>.{json,md}`), `synthesize` (сводный отчёт), сборка PDF, построители доказательств. |
| `source/harness/orchestration/run.py` | Оркестратор: разбор команд, единый драйвер запуска, сборка отчёта. |
| `source/harness/config/` | Настройки: `target.yaml` (описание цели), `models.yaml` (модели), `payloads.yaml`, `hypotheses.yaml`. |
| `docs/` | Документация: как писать модуль атаки, архитектура, методы, результаты. |
| `output/` | Результаты прогонов (в git не хранятся): `runs/<прогон>/<модуль>/…` и сводный `REPORT_<прогон>.{md,pdf}`. |

Файл `.env` (ключ `OPENROUTER_API_KEY`) и каталог `fixtures/` (`keys.json`, `success_corpus.json`)
в git не входят.

## Установка

```bash
python3 -m venv .venv
./.venv/bin/python -m pip install pymongo redis requests pyyaml weasyprint markdown
echo "OPENROUTER_API_KEY=sk-or-..." > .env
```

Отдельного `requirements.txt` в репозитории нет — зависимости ставятся командой выше. Ключ из
`.env` подхватывается автоматически. Тестируемый стенд (mongo, redis, агент, сервис данных)
должен быть запущен; его адреса и порты берутся из `config/target.yaml`. Сборка PDF требует
пакетов `weasyprint` и `markdown`; если их нет, отчёт остаётся в формате Markdown.

## Запуск

Всё запускается через корневой `run.py` — он добавляет `source/` в путь импорта и передаёт
управление оркестратору.

Основной способ — по имени модуля:

```bash
./.venv/bin/python run.py --list                   # список всех модулей и их параметров
./.venv/bin/python run.py a-bac                     # один модуль
./.venv/bin/python run.py a-bac a-docinject         # несколько модулей
./.venv/bin/python run.py a-all                     # все активные модули (включая обёртки внешних инструментов)
./.venv/bin/python run.py a-all-nowrapper           # все активные, кроме обёрток внешних инструментов
./.venv/bin/python run.py a-docinject docinject--mode=stealth docinject--attempts=8
```

Имя модуля задаётся как `a-<имя>` (по названию его папки). Параметр модуля переопределяется
записью `<имя>--<ключ>=<значение>`: оркестратор убирает префикс `<имя>--`, и модуль получает
чистый ключ. Неизвестный ключ даёт предупреждение, а не ошибку. Значения по умолчанию лежат в
файле `params.yaml` внутри модуля.

Полный цикл — прогон и сводный отчёт по нему:

```bash
./.venv/bin/python run.py a-all        # 1) прогон: runs/<прогон>/<модуль>/report__<имя>.{json,md}
./.venv/bin/python run.py report       # 2) сводный отчёт по этому прогону: output/REPORT_<прогон>.{md,pdf}
```

То же одной командой — флаг `--report` собирает отчёт сразу после прогона:

```bash
./.venv/bin/python run.py a-all --report
```

Неактивные модули (см. таблицу ниже) в `a-all` не входят — их вызывают по имени: `a-mem`,
`a-chain`, `a-docinject_oracle`, `a-directinject_oracle`.

### Одна папка на прогон

Каждый прогон пишется в одну папку `runs/<прогон>/`. Она запоминается (указатель `runs/CURRENT`)
и переиспользуется следующими вызовами. Каждый модуль пишет в свою подпапку
`runs/<прогон>/<модуль>/`, поэтому несколько запусков, в том числе параллельных, не мешают друг
другу, а команда `report` собирает отчёт по всей папке.

```bash
./.venv/bin/python run.py new --run camp1   # начать именованную папку и запомнить её
./.venv/bin/python run.py a-bac             # пишет в runs/camp1/bac/ (папка берётся из CURRENT)
./.venv/bin/python run.py a-docinject       # пишет в runs/camp1/docinject/ (та же папка)
./.venv/bin/python run.py where             # показать текущую папку и её модули
./.venv/bin/python run.py report            # отчёт по runs/camp1/ + копия в output/REPORT_<прогон>.{md,pdf}
```

- `run.py new [--run <имя>]` — начать новую папку (по метке времени или по имени) и запомнить её.
- `--run <имя>` у `a-*` и `report` — явно указать папку. Несколько запусков с одним именем пишут
  в одну папку без конфликтов.
- `--new` у `a-*` — принудительно создать новую папку для этого прогона.
- `--report` у `a-*` — собрать сводный отчёт сразу после прогона.
- Без флагов `a-*` берёт запомненную папку (`CURRENT`); если её нет — создаёт новую и запоминает.
- `report` пишет отчёт в саму папку прогона и копию в общий каталог `output/`.

### Прочие команды

```bash
./.venv/bin/python run.py smoke              # быстрая проверка без модели: доступы, чат, проверка состояния, очистка
./.venv/bin/python run.py mem [--marker X]   # показать состояние ярусов памяти
./.venv/bin/python run.py report             # пересобрать сводный отчёт из готовых report__*.json
# старые команды с плоским выводом: bac, poison, chain, bac-proof, poison-proof, llm-repro, models, repro
```

Пометка «активен» означает, что модуль входит в `a-all`; остальные вызываются по имени.
Обёртки внешних инструментов активны, но не входят в `a-all-nowrapper` (быстрый прогон без
внешних зависимостей).

|---|---|---|---|---|

| `a05_direct_leak` | BAC | Данные чужого клиента в ответе без вызова инструмента | Отпечаток другого клиента в ответе | да |
| `docinject` | Отравление | Внедрение инструкции через документ, поданный «на анализ» | Запись закрепилась в памяти и включилась в контекст; повторная проверка в новом диалоге | да |
| `directinject` | Отравление | То же, но прямым сообщением | Запись закрепилась и включилась в контекст; повторная проверка в новом диалоге | да |

| `g03_register` | Вариативность | Влияние формулировки (приказ или описание) против встречной записи | Запись закрепилась, с разбивкой по формулировкам | да |

| `directinject_oracle` | Отравление | `directinject` с таким же подбором | То же | нет |

| `garak` | Обёртка | Внешний инструмент garak (внедрение в промпт) | Вывод инструмента, перепроверенный сильной моделью | да (обёртка) |
| `deepteam` | Обёртка | Внешний инструмент deepteam (избыточные полномочия, инъекция) | Оценка риска, перепроверенная сильной моделью | да (обёртка) |
| `llamator` | Обёртка | Внешний инструмент red-team по чату (утечка промпта, соглашательство, логика) | Вывод инструмента, перепроверенный сильной моделью | да (обёртка) |

Обёртки (`garak`, `deepteam`, `llamator`) — это обычные модули с признаком обёртки. Движок лежит
в `source/harness/tool_wrappers/`, тонкий переходник — в `attack_vectors/_toolbase.py`. Вердикт
обёртки — это оценка вспомогательной модели, а не проверка по состоянию, поэтому в число
подтверждённых уязвимостей он не входит: находка отмечается доказанной только после независимой
перепроверки. Обёрткам нужны свои окружения (см. `config/models.yaml`) и запущенный стенд; если
их нет, обёртка работает в урезанном режиме и пишет отчёт с пометкой «не подтверждено».

## Трейсер памяти

Для атак на память результат определяет отдельный внешний трейсер — проект `yaml-memory-tracer`.
Это чёрный ящик: инструмент его не запускает и не читает базы стенда в поисках метки — он читает
только журнал трейсера в формате JSONL. Путь к журналу и привязка задаются в `config/target.yaml`,
в разделе `tracer` (`file` — путь к журналу; `target` — фильтр записей; при необходимости
`landing_map` — таблица «метод хранилища → ярус памяти»). Разбор журнала выполняет класс
`TraceAnalyzer` из `source/harness/oracle/tracer.py`; в модуле он доступен через `ctx.tracer()`.

Результат атаки на память подтверждается двумя независимыми способами:

- **Журнал трейсера** показывает, каким методом и на какой ярус памяти записана метка.
- **Повторный вопрос** тому же агенту в новом диалоге или от другого клиента: если метка снова
  всплывает в ответе, эффект сохраняется. Прямое чтение метки из базы данных для этого не
  используется. Сброс стенда между пробами выполняется отдельным скриптом.

Каждая успешная проба сохраняет свой участок журнала в подпапку `traces/` рядом с результатами
модуля (`runs/<прогон>/<модуль>/traces/trace_<время>_<метка>.jsonl`), а отчёт ссылается на этот
файл. По нему видно точное место, где закрепилась внедрённая запись. Если журнала нет или он
пуст, модуль переходит в урезанный режим проверки. Сам трейсер — отдельный репозиторий и в этот
проект не входит.

## Где лежат результаты

```
output/runs/CURRENT                 указатель на текущую папку прогона
output/runs/<прогон>/               одна папка на прогон (по метке времени или имени из --run)
  <модуль>/                         подпапка на модуль
    report__<модуль>.json           результат в строгой схеме (для сборки сводного отчёта)
    report__<модуль>.md             читаемый отчёт модуля, включая раздел о сохранённых трассировках
    findings.json                   находки модуля для общего свода прогона
    summary.json, attempts.jsonl, calls.jsonl, proof.md
    traces/                         трассировки успешных атак на память: trace_<время>_<метка>.jsonl
  findings.json, findings.md, coverage.*, attempts.jsonl   свод по всей папке
  REPORT_<прогон>.md / .pdf         сводный отчёт этого прогона
output/REPORT_<прогон>.md / .pdf    копия отчёта последнего прогона в общем каталоге
```

Каждый модуль всегда пишет `report__<имя>.{json,md}`: драйвер вызывает `report_std` даже если сам
модуль упал (тогда с записью об ошибке). Отрицательный результат помечается как «не подтверждено»,
а не как «безопасно». Свод по папке пересобирается из подпапок модулей при каждом вызове, поэтому
последний завершившийся запуск восстанавливает полную картину. Файлы записываются атомарно (через
временный файл), так что параллельный запуск не увидит наполовину записанный файл.

## Сводный отчёт по уязвимостям

**Где взять.** Отчёт этого прогона — `output/runs/<прогон>/REPORT_<прогон>.{md,pdf}`. Копия отчёта
последнего прогона — `output/REPORT_<прогон>.{md,pdf}`. Исходные отчёты модулей, из которых он
собран, — `output/runs/<прогон>/<модуль>/report__<имя>.{json,md}`. Какой прогон попадёт в отчёт:
указанный через `--run`, иначе запомненный (`CURRENT`), иначе самый свежий (`run.py where` покажет
текущий).

**Как собирается.** Сначала прогон записывает результат каждого модуля в `report__<имя>.json` в
единой схеме; вердикт в нём даёт проверка по состоянию, не модель. Затем `run.py report` по одной
папке прогона: читает результаты всех модулей, оставляет только подтверждённые находки, и сильная
модель (по умолчанию `claude-sonnet-5`, можно заменить флагом `--model`) пишет резюме по уровням
серьёзности и описания уязвимостей со сведением дублей и указанием, какие модули подтвердили
находку. Если модель недоступна, тот же отчёт собирается по данным без неё. Разделы про внешние
инструменты и итоговую таблицу по модулям строит код, а не модель. Затем отчёт переводится в PDF.

Важно: модель только формулирует текст и сводит повторы. Вердикт, раздел про внешние инструменты
и таблица по модулям — не на усмотрение модели. Отчёт можно пересобрать в любой момент командой
`run.py report`, не перезапуская атаки.

**Отдельная сборка отчёта.** Отчётник можно запустить на любой папке с файлами `report__*.json`:

```bash
./.venv/bin/python run.py report --dir <папка> [--model anthropic/claude-opus-4.6]
PYTHONPATH=source ./.venv/bin/python -m harness.report.synthesize <папка> [--model ...] [--no-pdf] [--to-output]
```

В папке прогона лежит `test_info.json` — технический манифест: команда запуска, время начала и
конца, цель, список модулей. Его пишет оркестратор, а отчётник берёт из него шапку. Если манифеста
нет, отчётник предупреждает, но собирает отчёт по имеющимся файлам.

**Что внутри отчёта.** Резюме по уровням серьёзности и ключевые риски. Список уязвимостей, каждая
со сведёнными дублями: суть и последствия простыми словами, чем подтверждена (проверка по
состоянию, доля успешных проб с доверительным интервалом), как воспроизвести, классификация OWASP,
какие модули подтвердили, а для атак на память — ссылка на файл трассировки с местом закрепления
записи. В конце — таблица по всем модулям прогона, чтобы ничего не потерялось.

## Как добавить свою атаку

1. Скопируйте `source/harness/attack_vectors/_template/` в `attack_vectors/<имя>/` (имя из строчных
   латинских букв, цифр и подчёркивания).
2. Заполните `vector.py` (наследник `AttackVector` с методами `run()` и `findings()`), `params.yaml`
   и `README.md`.
3. Модуль сразу появляется в `run.py --list` и запускается как `a-<имя>` — править ядро не нужно.

Полное руководство автора модуля (контракт, проверка результата, параметры, обработка сбоев,
чек-лист) — в `docs/ATTACK_VECTORS.md`. Родственные модули отравления могут наследовать общую базу
`attack_vectors/_docbase.py` (готовый ход пробы, повторная проверка в новом диалоге и подбор
формулировок по результату).

## Настройка на другую цель

- `config/target.yaml` — единственный источник сведений о цели: адреса, учётные записи для посева
  данных, режимы авторизации, ярусы и лимиты памяти, триггеры консолидации. Смена цели — это правка
  одного этого файла.
- `config/models.yaml` — модели по ролям: переписывание атак, судья, отчёт, целевые модели.
- `config/payloads.yaml` и `config/hypotheses.yaml` — формулировки, наборы и проверяемые гипотезы.
