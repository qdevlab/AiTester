## Что за проект
`aitest_cui` (`/home/dev/aitest_cui`, пакет `source/harness/`) — конфиг-driven грей-бокс харнесс
тестирования GenAI-агента с многоярусной памятью. Изолированный стенд `genai-cui` (порты 9xxx).
Контекст — memory: `aitest-cui-attack-vectors`, `aitest-cui-isolated-stand`, `genai-harness-tool`,
`genai-sectest-mempoison-test`.

## Модульная система атак (куда встраивать тул)
Атака = папка `source/harness/attack_vectors/<name>/` (`vector.py` подкласс `AttackVector` +
`params.yaml` + `README.md`), подхватывается без регистрации. Память-атаки: **`mem`** (отравление
E1..E4) и **`chain`** (связка A×B через память). Общий контекст `VectorContext` (`ctx`) уже даёт
ленивые сервисы (`ctx.client()/attacker()/judge()`). Дока автора: `docs/ATTACK_VECTORS.md`.

## Идея
Набор ВСПОМОГАТЕЛЬНЫХ тулов для атак. Первый — **трейсер памяти**: проследить жизненный путь
внедрённого элемента по ярусам (working redis → finalize/консолидация → policy/semantic/episodic/
dialog), т.е. E1→E2→E3→E4 и конвейер `finalize→EXTRACT_SEMANTICS→persist`. Уже есть смежное:
`oracle/memory_observer.py`, `oracle/state.py` (`snapshot`, `find_marker`, `marker_in_victim_context`).
Вопрос — что трейсер добавляет сверх них (таймлайн/дифф/причинность/визуализация?).

## Принцип интеграции (решение юзера)
Модули памяти (`mem`/`chain`) **используют трейсер, ЕСЛИ он есть** — опциональная зависимость:
present → обогащают вывод трейсом; absent → работают как сейчас (graceful degrade). Скорее всего —
опциональный сервис на `ctx` (напр. `ctx.tracer()` → объект или `None`). Планируем сейчас,
«дружим» позже.

## Как двигаемся
Юзер даст проект/наработку трейсера на анализ → я смотрю, как его аккуратно «подружить» с харнессом
(контракт, где висит на `ctx`, как модули опционально зовут, конфиг-driven, без слома при отсутствии).

## Инварианты (не ломаем)
Config-driven (ноль литералов, всё через `cfg`); наш детерминированный оракул состояния остаётся
рефери; переносимость (`target.yaml` = правда о цели); трейсер — вспомогательный, не заменяет оракул.
