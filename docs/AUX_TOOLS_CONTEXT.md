## Что за проект
`aitest_cui` (`/home/dev/aitest_cui`, пакет `source/harness/`) — инструмент тестирования
GenAI-агента с многоярусной памятью; все сведения о цели берутся из настроек, доступ к системам
на уровне серого ящика. Изолированный стенд — `genai-cui` (порты 9xxx). Сопутствующий контекст в
памяти: `aitest-cui-attack-vectors`, `aitest-cui-isolated-stand`, `genai-harness-tool`,
`genai-sectest-mempoison-test`.

## Модульная система атак (куда встраивать инструмент)
Атака — это папка `source/harness/attack_vectors/<имя>/` (`vector.py` с подклассом `AttackVector`,
плюс `params.yaml` и `README.md`); инструмент подхватывает её без регистрации. Атаки на память:
**`mem`** (отравление по стадиям) и **`chain`** (связка A×B через память). Общий контекст
`VectorContext` (`ctx`) уже отдаёт сервисы по мере надобности (`ctx.client()`, `ctx.attacker()`,
`ctx.judge()`). Руководство автора модуля — `docs/ATTACK_VECTORS.md`.

## Идея
Нужен набор вспомогательных инструментов для атак. Первый из них — трейсер памяти: он должен
проследить путь внедрённой записи по ярусам (рабочая память в redis, затем финализация и
консолидация, затем ярусы политики, семантики, эпизодов, диалогов), то есть всю цепочку
`finalize`, извлечение смысла (`EXTRACT_SEMANTICS`) и закрепление. Что-то похожее уже есть:
`oracle/memory_observer.py` и `oracle/state.py` (`snapshot`, `find_marker`,
`marker_in_victim_context`). Вопрос в том, что трейсер добавляет сверх них — временную линию,
разницу состояний, причинность, наглядную картинку?

## Как договорились подключать (решение пользователя)
Модули памяти (`mem`, `chain`) используют трейсер, если он есть, — это необязательная
зависимость: есть трейсер — обогащают вывод трассировкой; нет — работают как сейчас, без сбоя.
Скорее всего это будет необязательный сервис на `ctx` (например, `ctx.tracer()` вернёт объект или
`None`). Планируем сейчас, связываем позже.

## Как двигаемся
Пользователь даст наработку трейсера на анализ, и дальше я смотрю, как аккуратно связать его с
инструментом: каким будет контракт, где он висит на `ctx`, как модули вызывают его по желанию,
как всё это настраивается файлами и не ломается, если трейсера нет.

## Что не ломаем
Всё через настройки (никаких литералов в коде, всё берётся из `cfg`); наша детерминированная
проверка по состоянию остаётся главным судьёй; переносимость (`target.yaml` — источник правды о
цели); трейсер — вспомогательный, он не заменяет проверку по состоянию.
