# Переносимость: как навести инструмент на другую цель

Инструмент не сшит с конкретной целью, и это видно по коду: в `harness/**.py` нет зашитых значений
цели. Порты, номера клиентов, имена коллекций, пути ручек, realm и секреты живут только в `config/`.
Проверить можно так:

```bash
grep -rnE '9600|37017|genai-stand|streamlit-ui|agent_policy_memories' source/harness --include=*.py \
  | grep -vE '/config|__main__|docstring|#'
# совпадения остаются только в комментариях, смоук-тестах и тексте находок — не в логике
```

## Как перенести (правим один файл)

1. Возьмите `customer_info.md` новой цели (от заказчика) — обычное текстовое описание.
2. Соберите из него `config/target.yaml` по той же схеме: адреса, режимы авторизации, выдача ключей,
   триггеры финализации, хранилища, инструменты, тестовые клиенты с эталоном, целевые модели
   (разделы `endpoints`, `auth_modes`, `provisioning`, `finalize_triggers`, `storage`, `tools`,
   `identities`, `target_models`). Это единственный обязательный файл для перенастройки — весь код
   читает цель отсюда, через `core/config.py`.
3. При необходимости подправьте `hypotheses.yaml` (участники и оси перебора) и `payloads.yaml`
   (наборы формулировок под домен новой цели).
4. Запустите `smoke`, затем `bac` и `poison`. `findings.json` самодостаточен для повтора на другом
   агенте.

Чего нет в `customer_info` — помечайте в `target.yaml` как `needs_review`, но не выдумывайте.

## Уровни проверки и работа при ограниченном доступе

Инструмент работает на трёх уровнях доступа. Чем меньше доступ, тем слабее проверка — но не до нуля:

| Доступ | BAC | Отравление памяти |
|---|---|---|
| **grey-box** (redis и mongo видны с хоста) | различие ярусов и прямое чтение | журнал трейсера и вопрос-ответ (основное); при таком доступе возможно и прямое сравнение ярусов `policy` и `semantic` — самый сильный вариант |
| **api-box** (только HTTP цели и выдача ключей) | `served_cross_cus` на сервисе данных токеном атакующего; отпечатки в ответе агента | ответ finalize (область видимости и факты), `GET /memory`, отпечатки в ответе жертвы |
| **black-box** (только чат-ручка) | отпечатки жертвы в ответе агента (через самого агента) | метка в ответе жертвы после finalize (воспроизведение), по разнице ответов |

Режим проверки записывается в саму находку: grey-box даёт доказательство по состоянию, black-box —
более слабое, по косвенным признакам. «Не воспроизвели на black-box» не равно «безопасно» (см.
цели-исключения в ТЗ).

Для этой цели grey-box доступен (redis:16379 и mongo:37017 проброшены наружу), поэтому используем
самую сильную проверку. Ручка `GET /memory` требует SSO-токен от oauth2-proxy, а путь без браузера
для неё не описан — это помечено как `needs_review`; без grey-box мы переключились бы на признаки
уровня api-box или black-box.

## Что переносится как есть, а что зависит от цели

- **Переносится без правок (механика):** транспорт, выдача ключей без браузера (шаблон «grant, затем
  mint, затем кэш»), проверка по состоянию (чтение ярусов по именам из конфига), сверка по нескольким
  отпечаткам, изоляция прогонов, атакующая модель, дифференциальный судья, отчёты. Ни одной правки
  кода.
- **Берётся из конфига (факты цели):** адреса и пути ручек, способ выдачи ключа, имена хранилищ и
  коллекций, список инструментов, тестовые клиенты с эталоном, названия моделей, лимиты подмешивания
  в контекст.
